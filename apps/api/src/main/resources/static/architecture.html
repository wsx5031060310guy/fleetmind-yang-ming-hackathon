AWS Architecture Blueprint

FleetMind 雲端架構 — 現行部署與方案比較

同一套「Speed Loss 節能決策支援系統」，可以落在很不同的 AWS 形狀上。這份報告先精確描述已上線的架構，再攤開四種替代方案的服務組成、資料流與取捨——讓「為什麼選這條路」有圖有據。

現行・已上線 Deployed today

現行ECS Fargate ＋ ALB ＋ Bedrock ＋ SNS/SES

單一 Spring Boot 服務同時吐 dashboard 與 16 個 REST 端點，跑在 Fargate 上、掛在 ALB 後面拿到永不變的網址。指標離線由 core-calc 算好、烤進映像；AI 解讀走 Bedrock，門檻告警同時發 SNS 與 SES。

使用者 → ALB:80 → Fargate 任務 → Bedrock / SNS + SES；ECR 那條虛線是部署路徑，real-metrics.json 在 build 時就烘進映像，請求路徑上沒有任何資料存放層。圖中組態 2026-07-15 自帳號 516665228894 讀回；標〔推導〕〔非讀回〕者除外——那是由讀回值推得或出自原始碼，依據寫在圖上該處。

Design decision

這套架構最不尋常的一點：請求路徑上沒有資料庫

指標不是執行期算的，也不是從資料庫撈的——real-metrics.json 在 build 時就烤進映像，執行期 RealDataService 直接讀映像裡的檔案。這不是「資料庫還沒接」：帳號今天實際 list 過，S3 0 個 bucket（全帳號）、DynamoDB 0 張表，Java 原始碼裡對這兩者是零引用，pom 內唯一的 AWS SDK 相依只有 bedrockruntime、sns、sesv2。ALB → 任務 → 讀檔，一條請求就走完了，中間沒有資料庫、沒有物件儲存、沒有快取層可以慢、可以壞。

這個取捨成立的前提，是資料集有界而且靜態。15 艘船、2021–2025 的正午報表、每艘每天一筆——這批資料交付後就不會再長。指標離線用 k = FOC / STW³（ISO 19030）算完就定版：S11 Speed Loss 21.8%（539 個有效日、距上次清洗 692 天）、S23 8.9%、告警門檻 10%。輸入既然不動，執行期就沒有東西需要重算或重查。換到的是：冷啟即有真資料、沒有連線池要暖、少一整類資料層故障模式，而且映像即資料版本——同一個 image 永遠吐同一組數字，部署完全可重現。

代價也很具體，而且會傳染到後面幾段。資料要更新就得重建映像 + 滾動部署，不是寫一筆 row（所以它不是即時系統）；更關鍵的是——沒有狀態，就沒有東西可以「跨區複製」。多區域 Active-Active 的前提是先把狀態外置到資料層，這正是多區域那一段今天走不了的第二個理由（第一個是帳號權限）。方案 B 與 E 之所以要引入 DynamoDB / S3，換的也正是這件事。

◆ 為什麼現在選它

  • 單服務、單一部署單位，導入與維運最省心
  • ALB 給永久網址，redeploy 網址不變、還自動健康接手
  • Fargate 免管機器，ARM64 便宜；1 task 就夠 demo
  • 指標離線算好烤進映像 → 執行期零重算、冷啟即服務

◆ 代價與已知限制

  • 指標更新要重建映像 + 滾動部署（非即時）
  • 常駐 1 task 有基本成本（非 scale-to-zero）
  • App Runner 在此 workshop 帳號被 AccessDenied，故走 ECS
  • 單服務放大到全船隊即時遙測時需再拆

方案 B Serverless

B全 Serverless — Lambda ＋ API Gateway ＋ DynamoDB

前端純靜態放 S3/CloudFront，API 走 API Gateway → Lambda，指標存 DynamoDB；每晚 EventBridge 觸發 Lambda 從 S3 重算指標。閒置零成本、隨流量自動伸縮。

閒置零成本 · 冷啟動是 Java Lambda 的主要取捨 · 重算受 15 分鐘函式上限約束。

◆ 優點

  • 閒置零成本，隨請求自動伸縮到零
  • 幾乎不用管機器與擴縮
  • S3 資料湖天然適合累積 5 年報表

◆ 缺點

  • Java 冷啟動延遲（可用 SnapStart 緩解）
  • 元件變多，除錯與追蹤更分散
  • 重運算受 Lambda 15 分鐘 / 記憶體上限
何時選它：要多租戶 SaaS 化、流量時高時低、想把成本壓到「有人看才付費」時。

方案 C Fully managed

CApp Runner — 最簡管理的容器托管

同一個容器映像，交給 App Runner 全托管：內建 HTTPS 網域、自動伸縮、免碰 ALB / VPC / 叢集。程式碼零改動即可上線。

程式零改動 · 本 workshop 帳號對 App Runner 回 AccessDenied，故正式選了 ECS。

◆ 優點

  • 最少的基礎設施：免 ALB、免 VPC、免叢集
  • 內建 HTTPS 與自動伸縮
  • 與現行同一份容器映像，遷移零成本

◆ 缺點

  • 可調參數少、網路控制弱
  • 部分帳號 / region 有權限或配額限制
  • 成本模型對長時間常駐不一定最省
何時選它：只想「把容器丟上去就有網址」、團隊不想碰網路層時，是最快的正式環境。

方案 D Self-managed

DEC2 ＋ Docker — 最省、最可控

一台 EC2 跑 Docker Compose + Nginx，綁 Elastic IP 拿固定入口。穩定負載下單位成本最低，代價是修補、監控、擴縮都自己扛。

單位成本最低 · 單台為單點風險，正式上線需自建監控與備援。

◆ 優點

  • 穩定負載下單位成本最低
  • 完整掌控 OS、網路、容器編排
  • 沒有平台黑箱，除錯直觀

◆ 缺點

  • 修補、監控、擴縮全自理
  • 單台是單點故障，要自建高可用
  • 維運人力成本高，不利小團隊
何時選它：負載穩定可預期、已有維運團隊、想把雲帳單壓到最低時。

方案 E Future / Scale-out

E完整資料分析管線 — 全船隊即時 ＋ BI ＋ ML

把眼光放到「不只 15 艘、不只正午一筆」：船端 IoT 即時遙測進 S3 資料湖，Glue/Lambda ETL，Timestream/Athena 查詢，QuickSight 給決策者 BI，SageMaker/Bedrock 做預測。這是規模化的終局形狀。

規模化終局：即時 + BI + 預測 · 對當前需求是過度設計，但畫出成長路線。

◆ 優點

  • 撐得住全船隊、即時遙測與多年歷史
  • QuickSight 讓非工程決策者也能自助分析
  • ETL / 查詢 / ML 各層可獨立擴縮

◆ 缺點

  • 元件多、建置與維運成本高
  • 對「15 艘 × 正午一筆」是明顯過度設計
  • 需要資料工程與 MLOps 能力
何時選它：從 demo 走向正式產品、要接船端即時資料與公司級 BI / 預測時的目標架構。

現況與規劃 Security

安資安：已收口的入口 ＋ 規劃中的縱深

縱深防禦是目標，但這頁把「已經在跑的」和「還沒做的」分開講——旁邊就是 live URL，寫得比實際好只會被 curl 拆穿。今天真正擋得住的是入口：Security Group 只放行 ALB，直打 task 公網 IP 已 timeout。其餘是下一步。

上半部除了標〔非讀回〕的 Shield Standard（AWS 於所有 ALB 預設自動生效，非我們部署）之外，每一項都附了當場可驗的證據；下半部四項都標了為何還沒有。

◆ 已實作（可驗證）

  • ALB 是唯一對外入口：fleetmind-sg 只放行 ALB SG 的 8080——直打 task 公網 IP :8080 已 timeout，走 ALB 仍 200
  • IAM 兩角色分離：execution role 拉 ECR／寫 log，task role 只有 Bedrock/SNS/SES——應用本身拉不到映像，也寫不了自己的 log group
  • SNS 綁死單一 topic ARN；動作已收斂（只有 InvokeModel，不是 bedrock:*）
  • CloudWatch Logs /fleetmind/api；Shield Standard 於 ALB 自動生效

◆ 誠實盤點 · 下一步

  • 不是私有子網：兩個子網皆 mapPublicIpOnLaunch=true，任務仍有公網 IP（無 NAT 時拉 ECR 需要）——收口靠 SG，不是子網隔離
  • 不宣稱「全面最小權限」：bedrock:InvokeModel 與 ses:SendEmail 仍是 Resource: *
  • 連線沒有加密：ALB 只有一個 HTTP:80 listener——curl -k https://… 逾時（000），curl http://… 才 200。收口擋的是「誰能連進來」，不是「連線內容看不看得到」。帳號內 Route 53 hosted zone 為 0，要上 TLS 得先有網域與憑證
  • WAF 與 Secrets Manager 尚未部署；GuardDuty 受本 workshop 帳號權限阻擋，我們開不了
  • 下一步：ALB 加 TLS listener（需先備網域與憑證）、任務移入私有子網＋NAT／VPC Endpoint、對外入口加 WAF、Bedrock/SES 收斂資源範圍

設計藍圖 · 未部署 Active-Active · DR

雙多區域 Active-Active：設計，不是現況

先說清楚：這一段全部還沒有蓋。現況是單一區域 us-east-1、一個 ALB、一個 ECS 服務、desiredCount 1；帳號裡 Route 53 hosted zone 0、DynamoDB 0 張表、EventBridge 0 條規則、S3 0 個 bucket。而且本次 workshop 帳號連跨區都不允許——ap-northeast-1 的 ECS 與 ECR 直接回 AccessDenied，這條路在比賽帳號上走不了。
但船隊本來就分佈在不同國家，這是貴司自有帳號上該長的樣子，所以照樣把它畫出來、講清楚取捨。

目標狀態（尚未部署）：兩區域同時服務、資料雙向複製；一區故障 Route 53 自動切換，另一區承接全量——無單一區域單點。圖下方「今日實況（已部署）· 單一區域 us-east-1」那一條，才是現在真的在跑的東西。

◆ 設計目標（提案）

  • Active-Active：兩區域皆服務，非冷備援
  • 各國船務端就近路由，延遲低
  • DynamoDB Global Tables 雙向複製，切換零資料遺失
  • Route 53 健康檢查偵測區域異常 → 自動 failover；S3 CRR 保存原始報表備份

◆ 為什麼今天沒有它

  • 比賽帳號不允許：ap-northeast-1 的 ECS / ECR 回 AccessDenied，跨區這條路在此帳號上不通
  • 要先有資料層：現行把 real-metrics.json 烤進映像、請求路徑上沒有任何資料存放層——沒有東西可以「跨區複製」。多區域的前提是先把狀態外置到 DynamoDB
  • 成本較單區高，且現階段尚未演練驗證 failover 真的會動；未經演練的災備等於沒有
  • 落地順序：先狀態外置 → 單區多 AZ（ALB 已跨 1d/1f）→ 再談雙區
