FleetMind 雲端架構 — 現行部署與方案比較

同一套「Speed Loss 節能決策支援系統」，可以落在很不同的 AWS 形狀上。這份報告先精確描述已上線的架構，再攤開五種替代方案的服務組成、資料流與取捨——讓「為什麼選這條路」有圖有據。

現行・已上線 Deployed today

現行ECS Fargate ＋ ALB ＋ Bedrock ＋ SNS

單一 Spring Boot 服務同時吐 dashboard 與 REST API，跑在 Fargate 上、掛在 ALB 後面拿到永不變的網址。指標離線由 core-calc 算好、烤進映像；AI 解讀走 Bedrock，門檻告警走 SNS。

資料流：正午報表 → core-calc 算 metrics → 烤映像 → ECR → ECS 拉取；使用者 → ALB → Fargate 服務 → Bedrock / SNS。

◆ 為什麼現在選它

  • 單服務、單一部署單位，賽程三天最省心
  • ALB 給永久網址，redeploy 網址不變、還自動健康接手
  • Fargate 免管機器，ARM64 便宜；1 task 就夠 demo
  • 指標離線算好烤進映像 → 執行期零重算、冷啟即服務

◆ 代價與已知限制

  • 指標更新要重建映像 + 滾動部署（非即時）
  • 常駐 1 task 有基本成本（非 scale-to-zero）
  • App Runner 在此 workshop 帳號被 AccessDenied，故走 ECS
  • 單服務放大到全船隊即時遙測時需再拆

方案 B Serverless

B全 Serverless — Lambda ＋ API Gateway ＋ DynamoDB

前端純靜態放 S3/CloudFront，API 走 API Gateway → Lambda，指標存 DynamoDB；每晚 EventBridge 觸發 Lambda 從 S3 重算指標。閒置零成本、隨流量自動伸縮。

閒置零成本 · 冷啟動是 Java Lambda 的主要取捨 · 重算受 15 分鐘函式上限約束。

◆ 優點

  • 閒置零成本，隨請求自動伸縮到零
  • 幾乎不用管機器與擴縮
  • S3 資料湖天然適合累積 5 年報表

◆ 缺點

  • Java 冷啟動延遲（可用 SnapStart 緩解）
  • 元件變多，除錯與追蹤更分散
  • 重運算受 Lambda 15 分鐘 / 記憶體上限
何時選它：要多租戶 SaaS 化、流量時高時低、想把成本壓到「有人看才付費」時。

方案 C Fully managed

CApp Runner — 最簡管理的容器托管

同一個容器映像，交給 App Runner 全托管：內建 HTTPS 網域、自動伸縮、免碰 ALB / VPC / 叢集。程式碼零改動即可上線。

程式零改動 · 本 workshop 帳號對 App Runner 回 AccessDenied，故正式選了 ECS。

◆ 優點

  • 最少的基礎設施：免 ALB、免 VPC、免叢集
  • 內建 HTTPS 與自動伸縮
  • 與現行同一份容器映像，遷移零成本

◆ 缺點

  • 可調參數少、網路控制弱
  • 部分帳號 / region 有權限或配額限制
  • 成本模型對長時間常駐不一定最省
何時選它：只想「把容器丟上去就有網址」、團隊不想碰網路層時，是最快的正式環境。

方案 D Self-managed

DEC2 ＋ Docker — 最省、最可控

一台 EC2 跑 Docker Compose + Nginx，綁 Elastic IP 拿固定入口。穩定負載下單位成本最低，代價是修補、監控、擴縮都自己扛。

單位成本最低 · 單台為單點風險，正式上線需自建監控與備援。

◆ 優點

  • 穩定負載下單位成本最低
  • 完整掌控 OS、網路、容器編排
  • 沒有平台黑箱，除錯直觀

◆ 缺點

  • 修補、監控、擴縮全自理
  • 單台是單點故障，要自建高可用
  • 維運人力成本高，不利小團隊
何時選它：負載穩定可預期、已有維運團隊、想把雲帳單壓到最低時。

方案 E Future / Scale-out

E完整資料分析管線 — 全船隊即時 ＋ BI ＋ ML

把眼光放到「不只 15 艘、不只正午一筆」：船端 IoT 即時遙測進 S3 資料湖，Glue/Lambda ETL，Timestream/Athena 查詢，QuickSight 給決策者 BI，SageMaker/Bedrock 做預測。這是規模化的終局形狀。

規模化終局：即時 + BI + 預測 · 對三天賽程是過度設計，但畫出成長路線。

◆ 優點

  • 撐得住全船隊、即時遙測與多年歷史
  • QuickSight 讓非工程決策者也能自助分析
  • ETL / 查詢 / ML 各層可獨立擴縮

◆ 缺點

  • 元件多、建置與維運成本高
  • 對「15 艘 × 正午一筆」是明顯過度設計
  • 需要資料工程與 MLOps 能力
何時選它：從 demo 走向正式產品、要接船端即時資料與公司級 BI / 預測時的目標架構。

縱深防禦 Security

安資安：VPC 隔離 ＋ GuardDuty 威脅偵測

船務資料敏感，安全不是加分是底線。VPC 把服務關進私有子網、只讓 ALB 對外；邊緣有 Shield/WAF，帳號層有 GuardDuty 持續偵測異常，憑證進 Secrets Manager、資料以 KMS 加密、所有動作留 CloudTrail、權限走 IAM 最小化。

縱深防禦：邊緣 → VPC 子網隔離 → 帳號級威脅偵測 → 加密/稽核/最小權限，逐層收斂攻擊面。

◆ 防護面

  • VPC 私有子網：ECS 無公網 IP，只有 ALB 對外
  • GuardDuty 持續偵測異常 API／外連／憑證濫用
  • Secrets Manager ＋ KMS：憑證不落地、資料加密
  • WAF/Shield 擋 L7 攻擊與 DDoS；CloudTrail 全稽核

◆ 落地順序

  • 先 VPC＋SG＋IAM 最小權限（現行已具雛形）
  • 再開 GuardDuty＋CloudTrail（近乎零維運）
  • 憑證遷入 Secrets Manager、S3/DynamoDB 啟用 KMS
  • 對外入口加 WAF；規模化再上 Shield Advanced

全球韌性 Active-Active · DR

雙多區域 Active-Active ＋ 即時告警與災備

船隊分佈不同國家，系統不能只活在一個區域。Route 53 依地理/延遲把各國船務端導到最近區域；亞洲與歐美兩區域同時 active-active，DynamoDB Global Tables 雙向複製，跨區 EventBridge 匯總即時告警，S3 跨區複製做備份；任一區域故障，健康檢查自動把全流量切到另一區，資料不丟。

兩區域同時服務、資料雙向複製；一區故障 Route 53 自動切換，另一區承接全量——無單一區域單點。

◆ 韌性與即時

  • Active-Active：兩區域皆服務，非冷備援
  • 各國船務端就近路由，延遲低
  • DynamoDB Global Tables 雙向複製，切換零資料遺失
  • 跨區 EventBridge 匯總告警，任一國事件即時通知

◆ 災備行為

  • Route 53 健康檢查偵測區域異常 → 自動 failover
  • S3 跨區複製（CRR）保存原始報表備份
  • 回復後資料自動回補、恢復雙活
  • 成本較單區高，但換全球可用性與合規落地
