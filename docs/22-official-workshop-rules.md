## 1. 環境（Environment Setup 頁）

- **Kiro**：AWS 的 AI 開發工具，官方建議賽前先裝好並註冊。每位參賽者有**固定 Kiro credit 額度**，需省著用。
- **AWS 帳號**：每組配發一個 AWS 帳號存取權（Workshop Studio 臨時帳號）；登入後確認右上角帳號號碼，全隊同一帳號。
- **Region**：開放 `us-east-1`（預設）與 `us-west-2`；遇 access denied 先檢查 region。
- **責任使用守則**（違反可能被回收帳號）：
  - S3 一律關閉公開存取（Block Public Access / Bucket Policy）。
  - **不得匯入任何個資／受規範資料／財務／健康／生物特徵／支付／惡意程式**等。
  - 不建 wide-open Security Group 的 EC2；不建 Public Access 的 RDS / EMR。
  - 只開工作所需的 instance 數量；Bedrock 請求需節流（大量運算會被 throttle，稍候即恢復）；只申請專案實際需要的 Bedrock 模型。
- **賽後**：帳號與資源由主辦**自動回收**，不負責保管——**需保留的資料/程式碼賽前自行備份**。

## 4. 陽明命題（官方框架）

**主題**：AI 船舶效能分析與節能決策支援系統。以匿名化航行日報 + 養護紀錄為基礎，理解效能變化與養護的關係並支援節能決策。

**採「Speed Loss 分析 + 油耗預測並行」，兩項產出**：

### 產出 A — 油耗預測模型（客觀/程式自動評分，25%）
- 給定某船某段航程的航行與環境條件，**預測當日主機全速油耗**。
- 同一模型要能**反事實推論**「現況下執行水下清潔（UWC）或螺旋槳拋光（PP）的節能效益」。
- 模型需：①從歷史學到「效能如何隨時間變化、又如何在養護後恢復」；②辨識各類養護/作業事件對運行與油耗的影響方式與程度；③**在只給部分可見特徵下，推估被遮蔽的油耗值**。

### 產出 B — Speed Loss Dashboard（專家品評，30%）
- 於 **ISO 19030** 框架下計算並視覺化 Speed Loss，呈現三項：
  - ① Speed Loss 趨勢（推進效能隨時間變化）；
  - ② Speed Loss 有多少百分比**因船體髒污**（**船殼 vs 螺旋槳的歸因**）；
  - ③ Speed Loss 與**水下清潔資料比對**（效能恢復/惡化時點是否對應養護事件）。

**官方明示提示**：資料中有一類事件是「**純檢查、無實體介入**」——不清洗、不拋光。好的模型應辨識**這類事件不應帶來效能改善**，而非把「養護後」一律當「變好」。

### 資料集
- **15 艘匿名船舶**的航行日報（含各航速/天候，僅排除純靠港/錨泊日以保連續日程供 Speed Loss 繪製）+ 所有船舶水下養護事件紀錄。
- 部分船舶養護後一段期間的效率/油耗被**遮蔽**（標記 `HIDDEN` / `PREDICT`）。**`PREDICT` 即待預測的油耗項目**。
- **被要求預測的日子條件**：全速航行 **≥22 小時**、風速 **≤4 級**、當日**單一燃料**。

### 提案簡報應涵蓋（本組加項）
- 互動化介面展現 Speed Loss 隨航程變化；
- 油耗預測建模方式與模型說明（含主要影響因子）；
- 希望額外取得哪些資料以強化決策/商務價值；
- AI 與 AWS 服務在此次黑客松扮演的角色。
